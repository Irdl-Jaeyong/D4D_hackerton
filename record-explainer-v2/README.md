# 합성 기록 열람·설명 데모 v2

> D4D 저장소에 추가된 최신 기록 대시보드입니다. 8000 Gazebo 백엔드에서 실제 카메라·기체 상태를 받아 표시하는 18081 대시보드입니다. 합성 기록 설명은 Qwen 모델을 사용하고, 실제 상태 브리핑은 텔레메트리를 코드로 집계합니다.
>
> 이 저장소에서는 `./scripts/setup_backend.sh`로 Python 환경을 준비한 뒤, 실행 중인 Ollama 서버를 지정하여 아래처럼 실행할 수 있습니다. Qwen 모델은 별도로 설치되어 있어야 합니다.
>
> ```bash
> D4D_OLLAMA_URL=http://127.0.0.1:11434/api/generate backend/.venv/bin/python -m uvicorn app:app --app-dir record-explainer-v2 --host 127.0.0.1 --port 18081
> ```
>
> 주소: http://127.0.0.1:18081 . 아래의 `.venv`, `local-tools`, `demo.py` 안내는 원본 작업 공간의 실행 배치를 설명합니다. 모델 파일과 로그는 저장소에 포함하지 않습니다.


## 합성 텍스트 재생

새 [재생 데모](PLAYBACK.md)는 미리 작성한 3단계 기록을 재생·일시정지·수동 진행하고, 단계별 스냅샷을 자동 또는 수동으로 요약한다. 기체 이동이나 Gazebo 데이터 연동은 아니다. 초기 고정 기록은 보존한다. 최신 Python 검사는 26개 통과했다.

## 전체 합성 기록 요약 추가

`전체 기록 요약 요청` 버튼은 필터·선택과 무관하게 고정 A/B/C 기록 3건을 한 모델 요청으로 설명한다. `/api/summary`에 빈 JSON `{}`를 POST한다. 원본의 ID·시각·정확한 인용과 함께 각 기록의 설명을 한 영역에 보여주고 원본으로 이동할 수 있다. 누락·중복·다른 기록 인용·잘못된 시각은 응답 전체를 거부한다. 개별 설명과 동일 생성 잠금을 사용하며 실패 후 재시도할 수 있다. LLM 표시를 끄면 요약 영역도 숨긴다.

현재 요약은 일반 합성 기록 전용이다. 실시간 기체 상태, 군사 상황·우선순위 판단, 제어, 자율 이동은 연결하지 않는다. Gazebo 통계도 요약 입력에 포함하지 않는다. 인용 검사로 의미 정확성을 보장하지 않는다. [검증 기록](SUMMARY_VERIFICATION.md)을 참고한다.

기존 `record-viewer-v1`은 그대로 보존했다. v2는 독립된 HTML/CSS/바닐라 JavaScript 화면과 FastAPI 백엔드다. 기록·LLM 경로는 합성 장치 A/B/C만 사용하며 실제 장치·ROS·외부 데이터와 연결되지 않는다. 별도 Gazebo 일반 통계 읽기 전용 영역을 추가했으며 합성 기록·LLM과 분리된다. 장치 명령·상태 변경·임무 실행 기능은 없다.

## 실행

### 최소 절차

프로젝트 루트에서 설치·모델·포트 사전 점검:

```bash
.venv/bin/python record-explainer-v2/demo.py check
```

시작:

```bash
.venv/bin/python record-explainer-v2/demo.py start
```

`준비 완료`를 확인한 뒤 사용자가 `http://127.0.0.1:18080`을 연다. 종료는 시작한 터미널에서 **Ctrl+C 한 번**이다. 시작 도구가 자신이 만든 Ollama·API 프로세스만 종료한다. 설치·모델 다운로드·서비스 등록을 자동 수행하지 않으며 기존 포트를 점유한 작업도 종료하지 않는다. 모델 파일 존재·크기는 확인하지만 암호학적 모델 무결성까지 확인하는 도구는 아니다.

사전 점검이 실패하면 표시된 이유를 해결한 뒤 다시 실행한다. 권한 제한으로 localhost 또는 GPU 접근이 안 되면 환경 관리자에게 확인하며 권한·보안 설정을 바꾸지 않는다. 정상 시작 중 모델 로딩 실패는 질문 영역의 오류로 표시되고 원본 조회는 유지된다. 로그는 `demo-ollama.log`, `demo-api.log`에 누적된다. 터미널을 강제 종료하거나 전원을 끄는 상황의 정리까지 보장하지는 않는다.

### 구성요소별 수동 실행

프로젝트 루트에서 첫 터미널에 Ollama를 수동 실행한다. 이미 실행 중인 서버가 있으면 종료하거나 덮어쓰지 말고 상태를 먼저 확인한다.

```bash
OLLAMA_HOST=127.0.0.1:11434 \
OLLAMA_MODELS="$(pwd)/local-tools/ollama/models" \
OLLAMA_CONTEXT_LENGTH=4096 \
OLLAMA_NO_CLOUD=1 \
local-tools/ollama/bin/ollama serve
```

두 번째 터미널에서:

```bash
.venv/bin/python -m uvicorn app:app --app-dir record-explainer-v2 --host 127.0.0.1 --port 18080
```

사용자는 브라우저에서 `http://127.0.0.1:18080`을 열 수 있다. HTML 파일 직접 열기는 API 연결 실행 방법이 아니다. 에이전트는 이전 브라우저 정책 차단에 따라 이 주소를 브라우저로 열지 않았다. 종료는 각 실행 터미널에서 Ctrl+C. 서비스 등록·자동 시작·외부 공개는 하지 않는다.

## 동작과 데이터 구분

- 카드 선택과 필터로 원본 기록 ID·발생 시각·내용을 확인한다.
- 읽음은 별도 표시다. 반복 표시도 원본 상태·해결 여부를 바꾸지 않는다. 읽음은 서버 메모리에만 보관되어 서버 재시작 시 초기화된다. 여러 페이지의 실시간 동기화는 구현하지 않았다.
- 질문마다 선택한 기록 하나와 읽음 표시만 모델에 전달한다. 이전 대화나 다른 기록은 모델 문맥에 추가하지 않는다.
- 생성 설명은 별도 누적 영역에 표시한다. 답변의 근거 ID·시각이 선택한 원본과 일치하는지 백엔드에서 검증한다. 생성 시각은 원본 발생 시각과 별도다.
- 설명 가능한 응답에는 원본 status/raw에서 그대로 복사한 인용을 요구한다. 인용이 없거나 원본에 없는 인용이면 502로 거부한다. 모델이 확인 불가로 표시하면 생성 문장을 쓰지 않고 고정된 근거 부족 안내를 표시한다. 인용 일치는 자유문 설명 전체의 사실 검증은 아니다.
- 채팅 이력은 페이지 메모리에만 있고 새로고침하면 사라진다. 필터 초기화는 읽음이나 질문 이력을 지우지 않는다.
- 없는 기록 404, 빈/긴 질문 422, 모델 미연결·미준비 503, 모델 시간 초과 504, 잘못된 근거·불완전한 응답 502를 반환한다. 기본 기록 조회는 모델과 독립적이다.
- 동시 생성 요청은 429로 안내한다. 각 질문은 최대 500자, 모델 문맥 4096, 생성 최대 500토큰, HTTP 읽기 타임아웃 45초다.
- 화면은 생성 중 요청 버튼을 비활성화한다. LLM 설명 영역 표시를 끄면 같은 원본·읽음 화면으로 LLM 보조 없이 확인할 수 있다. 영역을 다시 켜도 원본은 바뀌지 않는다.
- 기록 새로고침은 초기 조회 실패 후 재시도와 서버의 읽음 상태 재확인에 사용한다. 실패하면 기존 원본 화면을 보존한다. 읽음 요청 중에는 새로고침을 막아 오래된 조회로 읽음 표시가 덮이지 않게 한다.
- 실패한 질문의 재시도 버튼은 그 질문의 원래 기록 ID·시각을 유지하며 새 이력 항목으로 추가한다. 현재 선택이 바뀌어도 늦게 온 답변은 이전 질문에 붙고 현재 원본 선택을 바꾸지 않는다. 응답의 근거 ID·시각은 화면에서도 다시 확인한다.
- 답변의 원본 확인 버튼은 필터를 전체로 바꾸고 해당 기록 상세로 이동한다. 카드·읽음 재렌더링의 포커스 유지를 구현했으나 실제 키보드 동작은 수동 확인 대상이다.
- 측정 시작/종료 버튼으로 경과 시간·UI 클릭 이벤트 수·질문 요청 수를 기록한다. 완료된 측정만 CSV로 내보낸다. 질문 문자열·원본 내용·이름·개인정보는 CSV에 포함하지 않는다. 현재 페이지 메모리에만 있어 새로고침하면 사라진다. 측정 중 조건 전환은 잠기며 모델 응답 대기 중 종료는 비활성화한다.

LLM은 추측하지 않도록 지시받지만 의미 수준의 사실 검증기는 아니다. 근거 ID·시각의 일치만으로 설명이 정확하다고 보장하지 않는다. 원본과 대조하는 데모이며 실제 상태 판단 근거로 취급하지 않는다.

## 검증

프로젝트 루트에서:

```bash
cd record-explainer-v2
../.venv/bin/python -m unittest -v test_api test_demo test_simulator
```

Ollama가 실행 중일 때 `../.venv/bin/python check_live.py`로 합성 API 검증을 수행한다. 자세한 수행 결과는 [VERIFICATION.md](VERIFICATION.md).

프론트엔드의 순수 상태 로직은 `state.js`에 분리했고 `state-tests.js`의 `runRecordStateTests()`로 검사한다. 이번에는 도구의 V8 JavaScript 런타임에서 두 파일을 순서대로 평가해 6개 검사를 수행했다. DOM·브라우저 실행 검사가 아니며 결과는 `frontend-test-results.json`에 기록했다. UI 스크립트 구문도 같은 런타임으로 확인했다.

사용자가 직접 확인할 [화면 체크리스트](SCREEN_CHECKLIST.md)와 [보조 유무 비교 절차](COMPARISON.md)를 함께 제공한다.

## 전체 과제에서 미구현인 범위

이 데모는 합성 기록 열람·설명 부분만 다룬다. 실제 UxV 연결, 임무 부여·분산·역할 할당·통제, 실제 환경 센서 데이터, Gazebo 장면 영상의 웹 표시·ROS 연동, 사람 개입 실행 경로, 인력 절감률·임무 성공률 측정은 구현·검증하지 않았다. 점군 스타일 시안도 실제 센서 기능이 아니다. 공중·지상·해상 모두 필수인지 등의 공식 해석 미결정 사항은 기존 문서를 따른다. 전체 해커톤 과제 완성이나 요구사항 충족을 주장하지 않는다.

최종 인계는 프로젝트 루트의 [HANDOFF.md](../HANDOFF.md)를 먼저 읽는다. 현재 Python 검사는 17개 통과했고, 종료 경쟁과 SIGTERM 정리를 보완하여 실제 시작·종료를 다시 확인했다. JavaScript 상태 검사 6개도 재통과했다. 브라우저 미검증 상태는 유지한다.
